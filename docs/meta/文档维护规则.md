## 内容分工与有效性

- wiki 按百科规范记录世界内已确定的事实；新增正文采用正向陈述，具体说明对象、行为、机制与处境。

- 已确定的内容与仍在讨论的有效方案分别标明状态。不采用、已过时、被否定的内容从正文、折叠区、附录、属性说明、示例和同步记录中删除；不通过负向例子、旧稿对照或修改说明再次复述。

- 只有作者正式声明可以留档作参考时，才保存相应内容，并标明许可范围和参考用途。编辑时不自动复制修改前全文作为备份。

## 一、编辑者的身份与语气

本节是**语气与身份的总纲**，优先于其余各节；其余条款冲突时，以「读起来像不像一部百科」为最终判据。

### 1.1 编辑者的身份（任务书《撰写口吻》）

| 要求 | 含义 | 禁止的表现 |
|---|---|---|
| **匿名与化名** | 编辑者以匿名或化名工作，保持匿名是编辑者的权利 | 以「我」「我们」发言；署名式表述 |
| **是编辑者，不是作者** | 本 wiki 没有「作者」，内容被视为群体创作的产物，不属于任何个人 | 以「作者」自居；把整理者的判断写成设定 |
| **中立的信息整理者** | 角色是中立地整理和呈现来自材料的设定，而非表达个人观点或原创研究 | 替设定下裁决；补写动机；写「整理者认为」 |
| **利益冲突规避** | 不替设定方美化或辩护 | 为设定缺陷找解释；把待定项包装成已定 |

> **关键推论**：整理者是**呈现者**，不是**创作参与者**。作者明确给出的设定应直接整理为正文事实；答复过程、版本取舍与整理者的推断不进正文，必要时记入 `meta/` 台账或任务报告。确有介绍价值的创作思路可收入可选的 `## 作者谈`，不将编务记录转存于该栏。

### 1.2 语气（任务书《撰写口吻》）

条目应采用**正式、客观、非个人化、冷静**的语气，遵循「新闻风格／摘要风格」，直白陈述事实。

- **第三人称叙述**：绝对避免第一人称「我」「我们」；**不直接称呼读者为「你」**。

- **中立无偏见**：对争议各方公平呈现，不暗示价值判断。

- **避免宣传与情感化**：不用宣传性、说教性、论证性口吻；用不带感情色彩的词。

- **警惕模糊措辞（weasel words）**：不用「一些研究者认为」「据说」「众所周知」一类无来源的模糊表述。

- **不写原创研究**：不写编辑者自己的主题分析、母题归纳、跨材料的「互文」论证——除非材料本身如此表述。

### 1.3 口吻的例外（任务书《撰写口吻2》）

本项目是**个人作品介绍项目**，因此：

> **允许措辞上俏皮一些**，可参考萌娘百科的编写风格。

**边界**：俏皮可以体现在**用词与句式的活泼**上，**不可以**突破 1.1 的身份定位与 1.2 的中立性——即：不得因俏皮而引入作者视角、个人评价、第一/第二人称或对编辑者的喊话。

### 1.4 元信息页的例外

`meta/` 下的文档（本文件、`维护说明.md`、`术语规范与别名对照.md`、`待决问题与冲突清单.md`、`Quartz站点维护说明.md`）**不是读者向条目**，其口吻应当**对编辑者说话**，不受 1.2 的第三人称与无墙禁令约束。但它们同样**不得模仿条目正文**、不得被条目正文引用为读者可见内容。

## 二、核心规则 raw 内容一律不标注「照抄」

**`raw/` 当中的所有内容都不应该标注照抄。**（作者对 GAP-009 的裁定）

只有在下列两类情况下，才**直接照抄**原文——且**照抄时不做任何标注**：

1. **原始文档自身有明确的照抄指示**，例如原文出现「这句话完成度很高，应该照抄」一类的表达；

2. **原文本身即为应当逐字保留的载体**，具体指：

   - **重要的角色台词**；

   - **世界观内的文本载体内容**，如报刊、书籍、公文、档案等虚构文本本身。

**其余一切情况，一律概括总结之后再纳入 wiki。**

普通设定以条目自身的叙述直接说明，不因其来自资料就逐句加引号或套引用块。引号与引用块用于确需呈现的台词、世界观内文献及其他必要原话，不用于包装整段普通介绍。

### 2.1 「不做任何标注」的含义

照抄时**不写**任何提示性标注。理由（作者原话）：

> 「原文如此」的标注本质上也是对任务书的引用，绝对不应出现在百科当中。而且本项目从未生成任何可以成为「原文」的正式作品。而且以编辑者视角来看，这是一种推卸词条编写真实性责任的措辞。

即：**标注「照抄」本身即预设了一个并不存在的「原文」**，属定性错误。照抄是编辑者的选择，不是对某个权威文本的转录。

## 三、内容层级的定义

（取代旧的「原文照录层」表述）

| 层级 | 位置 | 定位 |
|---|---|---|
| 正式条目 | `wiki/01-` ~ `wiki/08-` | 读者向的规范化条目，正文只陈述有据事实 |
| 素材整理层 | `wiki/09-作品与写作素材/` | 对 raw 材料做**规范化整理与总结**后的记录；不是原文副本 |
| 模板 | `wiki/_templates/` | 新建条目的骨架与体例规则 |
| 元信息层 | `meta/` | 面向编辑者的仓库说明、术语规范、冲突台账、本规则 |

**「素材整理层」的写法**：先给概述（本页收录什么、出自哪类材料），再写**整理后的内容**；确需逐字保留的台词或世界观内文本，按第二节直接引录、不加标注。

**栏目按内容设置**：取消每条固定附加「考据／词条历史／作者谈」三栏的要求。有实际内容时，可在文末设置 `## 考据`（有依据的现实原型／灵感来源）和 `## 作者谈`（有介绍价值的创作思路与期待）；无内容则省略，不写「无」「暂无」「待补」来凑齐结构。

**不再预设 `## 词条历史`、`### 版本与分歧`、`### 来源与整理注记` 或 `## 整理注记`**。修订沿革由 Git 保存；必要的来源核对、版本比较和待决问题记入 `meta/` 或任务报告。不得为符合旧模板而恢复作者已删除的栏目，也不得将其中的编务记录转移到「考据」「作者谈」。

**不写「> 分类：…」装饰行**：条目类型由 frontmatter 的 `type` 承担，目录归属由文件路径承担，不需要在正文首行写「分类：角色 · 目录 `04-人物角色/`」。该行曾由模板统一预置而在 54 个文件中扩散，已于 2026-10 全库清除。

## 四、开发向信息的处置

**面向开发者的信息，在确认不影响作品内容信息的前提下，全部删除。**（作者对 GAP-007 的裁定；判据取 GAP-010 候选 B）

### 4.1 一律删除

- 编辑工作流程与编务处置意见（「建议后续剥离为创作手记」「先命名再立页」等）

- 平台导出残留（平台名、页码、文件 ID、字节数、导出校对）

- 内部编号（CONF/Q/H/B 系列）

- 编辑待办与指令（待补、待确认、勿臆断）

- 校对注与照录声明（见第二节）

- 编辑方法论说明（按规则、本库、为讨论材料而非正文）

- 格式示例性的错误措辞

- 版本沿革、已解决的分歧比较、来源合并与别名归一过程；不以文末栏目重新收容这些编务记录

### 4.2 保留并改写为读者向表述

- **体裁**：说明本页属于何种材料（作品片段、档案、摘编）

- **完整性**：材料是否完整、截断于何处——用一句话陈述事实，不写「原文如此」

- **作者明确给出且影响作品内容的设定**

### 4.3 边界

判据未覆盖的情形，不自行删除作品内容信息；必要的疑问记入 `meta/待决问题与冲突清单.md` 或任务报告，不在读者页面添加「待确认」标记。「不影响作品内容信息」是删除的前提，不是事后的辩解。

来源追踪统一保留于编辑台账，不在页面头部设置 `source` 字段，也不将来源路径复制到正文。作者已经手动删除的页面和内容不因旧索引或旧来源仍有记录而自动恢复；具体收录边界见 7.6。

## 五、文件命名与元数据

### 5.1 文件命名

1. **文件名 = 规范名**，不含书名号、全角括号、叹号等标题性标点。原名标点保留在 `title` 字段与正文中。

   - 例：`《公民宪法》.md` → `公民宪法.md`；`请问有什么工作吗！.md` → `请问有什么工作吗.md`

2. 原名中的连字符、数字等非标题性字符保留（如 `Falcon-1780-DM.md`）。

3. 文件名与 `title` 不含「AI稿」等制作过程标签。稿件状态用 `canon` 固定词表表示；确需记录的制作来源与取舍过程放入编辑台账，不把「AI稿」写成 `canon` 枚举值。

4. **同一事件只设一条条目**；别名写入 `aliases`，不另立页面。

5. 改名后**同步更新全部入链**与 `wiki/00-导览与索引/总索引.md`。

### 5.2 元数据（frontmatter）

1. frontmatter 是条目的一部分，**其行内注释与正文同等受第四墙禁令约束**——不得在 `#` 注释中写内部编号、平台名或整理判断。

2. 字段本身可以留空，**空值不写说明**。

3. `title` 是页面标题，**不得写入开发注记**（如「（暂名）」「（名字待定）」）或状态词。

4. `title` 必须与文件名（规范名）一致。

5. `aliases` 只写纯名；必要的出处、平台、沿革说明记入 `meta/` 的术语表或任务报告，不写入条目正文。

6. 固定词表不得越界：

   - `type`：角色 / 组织 / 地点 / 历史事件 / 物品 / 概念 / 作品 / 写作素材

   - `status`：完整 / 较完整 / 草稿 / 骨架

   - `canon`：正典 / 存疑 / 旧稿 / 弃稿

   - 不得把说明文字塞进上述枚举值；`tags` 用子线名，不得混入来源或稿次属性。

### 5.3 链接与交叉引用

1. 一律用**标准 Markdown 相对链接** `[名](相对路径.md)`；**不使用** `[[双链]]` 语法。

2. **链接文字用规范名**（如 `[柏格宁房东](…)`，不写「莉雅」）。

3. 提到其他条目时**必须加链接**，不得只写「参见某条目」而不给链接（软引用）。

4. 文档中的**格式示例要包在反引号内**（写作 `` `[名](路径)` ``），否则会被解析为真实链接而产生断链。

5. 交付前确认无断链：目标文件必须存在。

6. 不为填满模板而附加 `## 关联条目` 列表。优先在相关叙述处添加必要链接，或使用已有主题导航；确有独立导航价值时可保留经过筛选的关联列表，不机械罗列所有沾边页面。

7. 交叉引用可以保留理解本条目所必需的简短背景，并链接到主条目；避免重复其详细机制、完整经历或无关信息。摘要须陈述与本条目直接有关的事实，不能借此引入跨材料推断。

8. 页面和模板的 frontmatter 不设置 `source` 字段。必要的来源定位、材料分工、具体章节和段落位置记录于编辑台账，路径须完整、可定位，不使用省略文件名或夹带说明。

9. `aliases` 仅记录同一对象的其他名称。上级、下属、产品、种族、泛称与有独立条目的不同身份阶段，通过关系说明和链接表达。

## 七、叙事与文风

本节是**写法层面的核心约束**。第 7.1–7.4 小节的详细约束共同针对同一类毛病：**用符号与缩写代替叙述**。问题不在于是否使用冒号、括号、箭头、列表或表格，而在于是否把本该由句子承担的说明责任推给了标点与排版。按内容选用表达形式，避免以名称和标签堆叠代替介绍。

### 7.0 编辑方式：只许逐条思考后写入，禁止脚本改稿（最高优先）

> **本条是整份规则中优先级最高的作业约束。与本节其余各条冲突时，以本条为准。**

**禁止用脚本对 `wiki/` 目录内的内容做增、删、改。**

唯一允许使用脚本的情形是**批量查找**（只读）：定位候选、统计命中、生成待办清单、比对版本差异。

**所有写入与删除操作，都必须由编辑者逐条阅读原句、思考后亲手写出文本。**

| 允许（只读） | 禁止（写入） |
|---|---|
| 全文搜索某个词或句式 | 用脚本替换某个词或句式 |
| 统计命中数量、列出文件与行号 | 用脚本批量改写措辞 |
| 与 git 版本做差异比对 | 用脚本批量删除行或段落 |
| 生成待核查清单 | 用脚本批量插入或补齐内容 |
| 校验链接、结构、断段是否合规 | 用脚本生成条目正文 |

#### 为什么

脚本改稿的事故模式是**结构性的，不是疏忽**：

1. **语义与载体不匹配。** 用「子串定位」的接口做「整行改写」，替换值里的完整句子会被塞进半个句子的位置，剩下的半句成为孤儿。本项目已发生过实际案例（`；原文并称` 被就地换成 `；该记载又称`，使原句残留为残片）。

2. **唯一性校验挡不住。** 「该子串出现几次」通过校验，与「该子串是否覆盖整行」是两回事；子串本来就只出现一次，校验必然通过。

3. **同一行多条规则会叠加。** 先改前缀、后改整行，第二条会以已被改动的行为基准，造成行首截断。

4. **错误是静默的、批量的。** 一处定位失误会在一次运行内扩散到多个文件，且不报错。

逐条思考后写入虽然慢，但每一步都有「读原句 → 判断 → 写新句」的强制核对，出错时也只会错一处、且当场可见。**这个代价必须付。**

#### 如何执行

1. **搜索**：用只读脚本或检索工具列出候选（文件＋行号＋原句），形成待办清单。

2. **逐条改写**：对每一处，读出原句与其上下文，思考后写出新句，用文本编辑操作改入。

3. **核对**：改完一处即回读该处，确认语义完整、无残留、无粘连。

4. **验证**：整批做完后，用只读脚本复跑断段与结构检测（见 7.5）。

5. **留痕**：通过 Git 差异记录修改，必要的「改了什么、为什么改」记入任务报告或 `meta/` 台账，不写回读者条目。

> **本条的由来**：本项目此前的多次清洗都采用脚本批量替换，累计造成了多处断段与残片，其中一部分直到作者发现才被查出。事故的根因不是脚本写得不够小心，而是**选错了工具**——「改写措辞」这件事本身需要逐条判断，不属于可脚本化的机械操作。

### 7.1 用叙述代替符号（硬约束）

| 禁止的写法 | 为什么不行 | 应当写成 |
|---|---|---|
| **冒号表介绍**：「能力：读心式意图之丝」 | 冒号把「名称」与「解释」拼在一起，读者拿到的是词条卡，不是句子 | 写成完整句子：「她的能力表现为看见他人身上涌出的丝线……」 |
| **括号表注解**：「读心（判断出于本能）」 | 括号把补充说明降格为附注，正是「滥用括号」的同类 | 把注解并入句子：「她对丝线的判断出于本能，像看见红色就知道那是红色」 |
| **箭头表因果/时序**：「报童扬名 → 被诱捕 → 入队」 | 箭头是流程图记号，不是行文 | 写成叙述：「她在柏格宁以报童之名扬名之后，何守向毒魔教团上报……最后入队」 |
| **顿号长串罗列**：「用途：察言观色、辨明谎言、找到躲藏的人」 | 罗列把语义压成标签堆，读者无法理解各项之间的关系与限度 | 逐项写成句子，说明各自的使用场景与限制 |
| **用表格取代机制说明** | 只列名称与标签，无法交代机制、前因后果与限制 | 机制说明用段落；基本信息、纪年、分类、分级及并列比较可用表格，必要时辅以解释 |
| **破折号插入长说明** | 与括号同类 | 并入句子，或另起一句 |

**判据**：把该段去掉所有标点符号后还剩多少信息？若剩下的是「名称＋标签」，就是符号化表达，必须改写。

本节约束的是用标点与排版代替说明的写法，不是禁止冒号、括号、列表或表格本身。列表项可以包含完整说明段落；确实便于比较的并列信息可以保留表格。

### 7.2 条目的丰满度（含量要求）

**有材料却只列名称与标签，是介绍不足。** 如仅写「能力：读心」而不解释已有的表现与机制，等同于没有介绍。材料本身有限时如实呈现，不以句数或字数判定质量，也不为扩写补造事实。

**参照标准**：`Input/御坂美琴 - 萌娘百科…html`（约 79 万字）展示了一部合格的角色条目应有的写法——**以连贯的叙事段落交代设定、经历与细节**，而非以短标签堆叠条目要点。不必追求同等篇幅，但须做到：

1. **按材料依据说明「是什么、怎么运作、边界在哪、对剧情意味着什么」**，而不是只给名称；资料没有给出的维度不强行补齐。

2. **经历类内容按时间顺序写成连续叙述**，有前因后果，不是要点罗列。

3. **关系类内容说明关系的性质与演变**，不是一句「与 X 相关」。

4. **能力类内容写成说明段落**：表现形态、触发条件、适用范围、已知限制、代价、故事中的作用。

5. 允许并鼓励**引用关键台词与场景**来支撑叙述（引用即照录，不加标注）。

以上维度以材料有据为前提，不要求逐项补齐。扩写应展开已有信息之间的关系、机制与影响，不凭空增加能力限制、动机、因果或剧情。材料有限时如实介绍，不为篇幅灌水；只有名字而无实际内容时，先判断是否需要单独立页（见 7.6）。

**自查**：把一个条目的正文读一遍，若读起来像**表单**而不是**介绍**，即为不合格。

### 7.3 条目间耦合的节制（硬约束）

**正文只陈述本条目自身的事实，不枚举其他条目所辖的内容。**

| 禁止 | 例子 | 应当写成 |
|---|---|---|
| 用归属角色的信息**反推**本条目设定 | `罗瓦伊.md`：「"罗瓦伊洲"：艾米莉为"在罗瓦伊洲的一个普通村庄里普通的9岁孩子"」 | 只写有依据的地理事实，例如「穆克希戈是罗瓦伊大陆上的一个国家」；不据单个角色补写地区的发展水平 |
| 在上级条目里**枚举下属** | 大洲条目罗列其境内的角色、组织、村镇 | 只写存在哪些**层级**与**已知区域名**，具体内容各归其条目 |
| 在组织条目里**枚举成员的全部事迹** | 小队条目复述每个成员的剧情 | 只写成员构成与队内分工；各人经历归各人条目 |
| 把关联条目的**判断**搬来当论据 | 「A 与 B 同名，故推断……」出现在 C 条目 | 未确认的推断记入编辑台账；C 只陈述与 C 直接相关的有据事实 |

**判据**：删掉该句后，本条目的信息是否受损？

- 若**不受损**（信息本属别的条目）→ 删除，改为一句归属陈述或一个链接。

- 若**受损** → 保留，但要写成关于本条目的陈述。

**理由**（作者 2026-10 指示）：跨条目引用归属角色的内容，会（一）造成条目间过耦合，一处改动牵动多处；（二）随着设定扩充，枚举必然膨胀失控；（三）从故事逻辑上讲，归属角色与上级地理单位之间只有归属关系，并无直接关联，把角色写进大洲正文是层级错置。

**允许的交叉引用**：句末链接可以指向相关条目；理解本条目所必需的背景可作简短摘要，并链接到主条目。摘要只保留直接相关的事实，详细内容仍由主条目承担。

总述页应介绍类别自身的共同特征与有依据的分类，不能将单个实例的能力、病症、身份或外观推广为整个类别的特征。必要的成员构成、区域归属与关系说明可以保留，不将本节解释为禁止一切交叉引用。

### 7.4 其余文风约束

1. **不用列表代替行文**：设定说明以段落陈述为主；列表只用于并列项、参数、步骤。

2. **不写绝对化叙事**：如「永远不会失败」「永远知道往后十步」——若为材料原文须加引号；否则改中立表述。

3. **不把角色内心独白与口语反诘直接写进正文**：改为第三人称客观陈述。

4. **不替设定下判断**：删去编辑者的裁决语（「不成立为……条目」「正史价值待作者定」）；已明确的设定直接陈述，必要的未决问题记入编辑台账。

5. **术语前后一致**：同一实体全篇用同一规范名；别名写入 `aliases`，必要的异写沿革记入术语表。

6. **板块职责不重叠**：同一事实不在「关系／经历／轶事」多节重复三遍。

7. **不写编辑交底**：删去「（设计人员语）」「原文未给生产背景」「（原文删除线句，转述大意）」等向读者交代来源动作的表述。

8. **中文标点用全角**：引号用 `“”`／`‘’`，不使用 ASCII 直引号 `"`／`'`；同一文件内不得混用。

9. **括注节制**：括号只用于必要的注解，不承担别名罗列、出处标注、校对说明、待定状态等功能。

10. **标题与表头直接命名内容**：如「性质」而非「性质（v0.0.2 作者答复）」。不在标题、表头和普通介绍中附带版本、制作过程、核对状态或猜测性问句。
